# Tray 录制状态响应优化

## 问题描述

使用 Tray 菜单开始/停止录制时，主窗口的录制状态（按钮样式、计时器）响应缓慢，存在明显卡顿。

## 原因分析

### 当前架构

```
Worker 线程循环（每50ms）:
    │
    ├─ 检查 quit_flag
    ├─ 检查 show_window_flag  
    ├─ 检查 screenshot_flag
    └─ 检查 recording_toggle_flag
           │
           └─ 若为录制中: 设置 is_recording = true
           └─ 若为停止: 设置 is_recording = false

GUI 更新循环（每100ms）:
    │
    └─ 读取 tray_state.is_recording
    └─ 计算 timer = start.elapsed()
    └─ 更新 UI 显示
```

### 瓶颈定位

1. **轮询间隔过长**
   - Worker: 50ms
   - GUI: 100ms
   - 最大响应延迟 ~150ms

2. **录制时 Worker 线程繁忙**
   - 录制时 Worker 每50ms轮询，处理帧数据耗时可能导致 sleep 延迟
   - `is_recording` 更新可能被延迟

3. **定时器计算开销**
   - 每次 `update()` 都调用 `start.elapsed()` 计算计时
   - 100ms 刷新间隔导致计时器"跳帧"

4. **菜单重建阻塞**
   - `set_menu()` 重建整个菜单在主线程执行
   - 可能短暂阻塞 UI

## 优化方案

### 方案 A: 缩短轮询间隔

| 项目 | 评估 |
|------|------|
| **改动** | Worker: 50ms → 10ms, GUI: 100ms → 50ms |
| **收益** | 响应延迟从 ~150ms 降至 ~60ms，用户体验明显提升 |
| **风险** | CPU 占用轻度增加：GUI 每50ms重绘 vs 原来100ms |
| **风险等级** | 低 - 现代硬件影响可忽略 |

### 方案 B: 录制时减少轮询

| 项目 | 评估 |
|------|------|
| **改动** | 录制时只检查 quit 和 show_window，跳过 screenshot_flag 等检查 |
| **收益** | 录制时减少约 50% 状态检查开销，Worker 更专注于录屏 |
| **风险** | 截图请求在录制中可能被延迟（但最大延迟仍<50ms，可接受） |
| **风险等级** | 低 - 分支逻辑简单清晰 |

### 方案 C: 计时器优化（简化版）

| 项目 | 评估 |
|------|------|
| **改动** | 用 `Arc<AtomicU64>` 存储 `start.elapsed().as_secs()`，GUI 根据原子秒数自己计算显示文本 |
| **收益** | 避免每次 update 都计算 elapsed，计时器更新更平滑 |
| **风险** | 需要跨线程共享计时器值，增加同步开销 |
| **风险等级** | 中 - 实现复杂度适中 |

**替代方案（不推荐）**：独立线程计算计时器文本，通过 `Arc<Mutex<String>>` 共享。风险：字符串跨线程传递增加复杂度，可能引入细微的计时器"跳变"。

### 方案 D: 异步菜单更新（不推荐）

| 项目 | 评估 |
|------|------|
| **改动** | 使用 `std::thread::spawn` 在后台线程调用 `set_menu()` |
| **收益** | UI 不阻塞，菜单重建在后台执行 |
| **风险** | ⚠️ **高风险**：`TrayIcon` 内部 `Rc<RefCell<...>>` 在多线程环境下操作可能触发竞态条件或未定义行为 |
| **风险等级** | **高** - 可能导致崩溃或 UI 无响应 |

**结论**：方案 D 风险过高，收益不明显，暂不实施。

## 综合建议

| 方案 | 推荐度 | 原因 |
|------|--------|------|
| A | ✅ 强烈推荐 | 简单有效，风险极低 |
| B | ✅ 推荐 | 简单有效，风险低 |
| C（简化版） | ✅ 推荐 | 用 AtomicU64 而非独立线程 |
| D | ❌ 不推荐 | 线程安全风险过高 |
